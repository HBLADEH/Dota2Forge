# 已发送战绩列表的有界选择状态

Category: architecture
Related task: [历史详情](../../tasks/active/2026-10-01-historical-match-detail.md)
Related code: [选择状态](../../../adapters/Dota2UID/src/Dota2UID/selection.py)
Related docs: [Dota2UID 命令](../../../docs/cookbook/dota2uid.md)

## Problem
只接受比赛 ID 不便于从刚返回的战绩选择单局；重新查询列表会消耗额度并可能改变序号。查询 100 场若自动发全部文本/图片会产生二十页。只在数据取得后保存状态又不能证明用户收到结果，且改绑/会话/并发可能把序号指向另一场。

## Decision
- Dota2UID 使用 `dota比赛 第N场`（1–100）和 `dota战绩 第N页`（1–20）。前者从已保存列表取绝对序号 ID，再通过独立详情服务查一次；后者读取同次数据，不发 Provider 请求。不解析 Unicode 数字、前导零或混合参数。
- RecentSelectionStore 只保存每个键最后一次有效结果，容量 128，写入后 600 秒 TTL，以注入的 monotonic 时钟计时；读取不续期。到期清理，超容量淘汰最早写入项，不持久化、无背景任务。这是宿主交互状态，不是来源缓存或新的查询策略。
- 键包含可信 namespace/platform/bot/account-user 身份、WS 连接、会话类型和会话 ID。GsCore Event.user_type=direct 使用调用者 user_id；group 使用 group_id；其他类型或缺失/非法会话字段明确拒绝选择。Core 身份和原绑定契约不改。
- 记住查询账号与完整绑定记录。选择时重新读取绑定并校验；改绑/解绑主动清空该身份全部会话，发送期间同身份改绑也使待提交结果失效。连接变化、停用和新 Runtime/重载不复用旧结果。绑定账号不参与该比赛就不标我方。
- Runtime.dispatch 串行查询/发送，最多接纳 16 个等待/在途 dispatch，过载给出固定提示且不查 Provider。完整回复发送成功后才提交结果；发送失败/取消传播、不重发，上一份有效列表保留。有效空结果成功发送后替换旧列表，序号明确越界。Runtime.handle 仅取文本、不确认发送，不能创建新选择状态。
- 每次查询仍支持 1–100 默认 10，但最初最多展示前两页（5 场/页）；其余提示用户显式取页。分段带绝对序号、比赛 ID 和直接查询方式。没有可靠会话字段时仍允许直接 ID/账号查询，但不保存列表并明确提示后续页不可用。
- 停用拒绝新 dispatch、取消在途查询/发送并清空状态；排队者不再发送。发送 API 是否真正被平台递送不由返回值保证，不承诺撤回已经递送的部分回复。新发现桥接显式传入会话字段并用 dispatch，既有宿主升级仍须先 stop 再替换/重载。

## Alternatives considered
- 查询成功就保存：发送失败时序号没有可见依据，改为完整发送后提交。
- 每次选择重新取 recent：序号可能漂移，选择已返回 ID。
- 所有账号共用列表或持久化列表：会话串用/保留过期个人数据，选择有界进程内状态。
- 一次发送二十页：影响会话阅读，保留现有查询上限并限制初始发送。

## Consequences
一次 Provider 成功但发送失败的列表不会替换旧有效列表；部分已发送消息不可自动撤销。缓存容量/TTL/连接失效规则是新交互契约，需要实机核对 GsCore 群/私聊字段。桥接升级、QQ 发送和图片渲染仍未验证；图片版式仍待明确确认。没有扩大来源缓存/自动重试/跨源回退范围。

## Verification
42项选择测试覆盖容量/TTL不续期、绑定记录变化、部署/用户/机器人/平台/连接/会话隔离、缺失会话、100场最后一页/序号、部分发送失败、有效空结果、失败查询、并发发送、发送期间改绑、队列上限和停用清理。全部使用合成数据与禁网MockTransport；最终统一705项通过，选择模块语句/分支100%，Dota2UID独立约96%；三包构建及隔离wheel验证通过。真实平台确认不由桩测试代替，新桥接尚未部署。
